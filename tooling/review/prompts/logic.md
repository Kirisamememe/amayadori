## 見る範囲

変更したコードが、決めた仕様のとおりに振る舞うか。仕様は、テストと `DECISIONS.md` に書いてある。

- 境界値、空・1件・上限、重複、並び順で、仕様と違う結果にならないか。
- load と route:公開 API が「無い」と返したもの(公開していないページ)を、404 にするか、ナビゲーションから外しているか。ページが表示に要る項目を、load の戻り値から欠いていないか。
- 想定内の失敗(`_tag` 付きの判別共用体で返す失敗)と想定外の失敗(throw して、SvelteKit がエラーのページとログにする失敗)の分け方が、呼ぶ側の扱いと合っているか。
- サーバーで描画した結果と、ブラウザで動かした結果が、食い違わないか。
- 件数が増えると実害が出る無駄(公開 API を1件ずつ呼ぶ、など)が無いか。
- tooling の検査とスクリプトが、決めたとおりに振る舞うか(止めるべきものを取りこぼさないか、正しいものを巻き添えで止めないか)。
- テストが仕様を確かめているか。実装をなぞるだけで、仕様を壊しても通るテストになっていないか。変えた振る舞いにテストがあるか。

## 見ない範囲

- 悪用につながる穴(Analemma とのつなぎ・ブラウザに届く値・入力の境界・秘密の扱い。セキュリティの観点)。入力の検証が仕様と違うだけで、悪用につながらないものは、この観点で見る。
- ページの見た目・操作・アクセシビリティ(UI/UX とアクセシビリティの観点)。
- 書き方・フォルダ・`DECISIONS.md` に書いたかなどの、リポジトリの約束(規約やルールの遵守の観点)。
- 文書・コメント・テストの名前・ページの文言の言葉(言葉の観点)。文書がコードと食い違っているときは、コードの方が仕様と違うときだけを書く。
